# Accessibility Contract

This contract applies to public visible FluentQt components. It turns existing
accessibility work into a consistent acceptance surface; it does not claim that
every current component already satisfies the full contract.

## Component contract

Each new or materially changed visible component must review the applicable
rows below.

| Area | Contract |
| --- | --- |
| Role | Use the native Qt accessible role when it matches. Composite/custom controls add a private adapter only when the base role is misleading. |
| Name | Application-provided `accessibleName` is authoritative. An automatic name may track visible text only while the value is empty or still equals the previous automatic value. |
| Description/value | Helper text, validation, progress, selection, and current value are exposed semantically without replacing application overrides or business values. |
| State | Disabled, read-only, checked, selected, current, expanded, modal, busy, invalid, and off-screen state match observable control state. |
| Focus/keyboard | Every pointer action has a documented keyboard path where the platform pattern supports it. Focus is reachable, visible, ordered, and returned after transient surfaces close. |
| Events | Emit accessibility events after real state changes. Repeated no-op setters and paint/theme refreshes do not announce duplicate changes. |
| Dynamic content | Insert/remove/reorder, popup open/close, toast/status announcements, and value changes notify assistive technology at the semantic object. |
| Model/view | Expose logical items, rows, cells, headers, counts, selection, and actions through model/view interfaces; never rely on a persistent widget per item. |
| Presentation | Light, Dark, high contrast, high DPI, reduced motion where supported, long text, and RTL keep focus and semantic state legible. |
| Compatibility | Qt-version-specific adapters are isolated in compatibility/private code and tested on the supported Qt matrix. |

## Ownership of accessible text

Automatic accessibility text follows the same rule already exercised by
Field, FlowView, Avatar, ToggleSwitch, PipsPager, Toast, and navigation
controls:

1. Record the last value generated by the component.
2. Replace it only when the current value is empty or still equals that last
   automatic value.
3. Once an application supplies a different name or description, preserve it
   across value, locale, theme, and layout changes.
4. Clearing an application override may opt back into automatic text only when
   the component API documents that behavior.

Visible labels alone are not a semantic contract. Icon-only actions need an
accessible name supplied by the component's translatable default or the
application. Library defaults remain empty when the project cannot provide a
correct localized label, as with custom Window caption tooltips.

## Events and tests

- Name focused tests `Contract_Accessibility*` so audits can find them.
- Query `QAccessible::queryAccessibleInterface()` for roles, names, values,
  state, child structure, and supported actions when Qt supplies an interface.
- Install an accessibility update handler only inside a scoped test helper and
  restore the previous handler. Assert event payloads only when accessibility
  delivery is active on the host.
- Test real transitions and no-op silence separately. Event assertions do not
  replace public signal assertions.
- Use logical model/view children for collection tests. A test that finds a
  `QWidget` for every item is evidence of the wrong architecture.
- Keep visual focus, RTL, text fit, and theme evidence in VisualCheck; do not
  use screenshots as proof of semantic roles or events.

## Logical navigation items

Breadcrumb, Pivot, SelectorBar, TabView, and PipsPager share one private
logical-item pattern rather than exposing their painted hit regions as an
opaque widget or creating a persistent widget for every item.

- Breadcrumb exposes ordered path items as links. The final item is the current
  location; earlier enabled items support the press action. Overflowed items
  remain in logical order and report off-screen state.
- Pivot, SelectorBar, TabView, and PipsPager expose a page-tab list with one
  page-tab child per logical item. Exactly the observable selected item reports
  selected state, and disabled or application-hidden items cannot be invoked.
- Item-provided accessible names override visible text without replacing the
  root widget's application-provided name or description.
- TabView exposes add as a named button action. Each tab exposes close when it
  is currently closable and previous/next move actions when reorder is enabled.
- PipsPager exposes every logical page, including pages outside the visible pip
  window, plus named previous/next actions. The visual window is not the
  semantic page count.
- Insert, remove, reorder, name, enabled/visible, selection, and logical-focus
  notifications are emitted only after effective changes. Theme, paint, and
  repeated no-op setters remain silent.

## Composite values

ToggleSwitch, RatingControl, NumberBox, ProgressBar, and ProgressRing expose
their application state as one semantic value instead of leaving assistive
technology to infer it from custom painting or internal child widgets.

- ToggleSwitch is a check box with checked state and the standard toggle
  action. Its automatic on/off description continues to yield to an
  application-provided description.
- RatingControl is a bounded slider. Accessible value `0` means no committed
  rating, the maximum follows `maxRating`, and the minimum step is one half
  star. Increase/decrease actions reuse the keyboard stepping behavior and are
  absent when disabled, read-only, or already at the applicable bound.
- NumberBox is a spin box that retains editable-text and text-selection
  interfaces while adding numeric current/minimum/maximum/step values and
  increase/decrease actions. NaN is an invalid value, and an infinite bound is
  exposed as unbounded rather than converted to a finite sentinel.
- ProgressBar and ProgressRing are read-only progress bars. Determinate mode
  exposes current/minimum/maximum values. Indeterminate mode has no numeric
  current value and reports busy/animated state only while the component is
  observably running; it never exposes value-changing actions.
- Application-provided names and descriptions remain authoritative. Header,
  caption, status, and formatted-value fallbacks are returned by the private
  adapter without writing over those QWidget properties.
- Current value, bounds, checked/read-only/invalid/busy state, and available
  actions notify only after an effective semantic change. Animation frames,
  paint/theme refreshes, and repeated no-op setters remain silent.

## Split actions

SplitButton and ToggleSplitButton expose one split-button semantic object with
two standard actions. The painted segments do not become persistent child
widgets or duplicate accessible children.

- The root role is `ButtonMenu`. SplitButton exposes `press` for the primary
  command, while ToggleSplitButton exposes `toggle` and reports checkable and
  checked state. Both expose `showMenu` only while an attached menu exists.
- Menu presence reports has-popup, expandable, and collapsed/expanded state;
  expanded follows the existing public `isOpen` value and therefore describes
  QMenu visibility rather than the same-window overlay phase model.
- `Space` invokes the primary action. `Alt+Down` and `F4` open the secondary
  menu through the same placement path used by pointer input. Opening the menu
  never emits the primary click or changes ToggleSplitButton checked state.
- Disabled controls expose neither primary nor menu actions. Removing or
  destroying the menu removes has-popup state and the `showMenu` action.
- Application-provided names and descriptions remain authoritative. Button
  text is only the fallback accessible name, including mnemonic stripping.
- Menu replacement, menu open/close, and checked-state changes notify only
  after effective changes. Repeated menu assignment, repeated visibility state,
  theme, paint, and geometry changes remain silent.

## Transient surfaces

Popup, Flyout, TeachingTip, and CoachMark expose the same-window surface that
already exists instead of creating a second accessible window or flattening
caller content into one generated string.

- Popup and Flyout are panes. TeachingTip and CoachMark are help balloons.
  Their native child widgets remain in the accessible tree, so headings,
  instructions, links, and buttons keep their own roles and actions.
- Application-provided root names and descriptions are authoritative. A
  generic surface never guesses a title from arbitrary child order. Actionable
  help surfaces should set a concise root name and description while retaining
  the full content as semantic child widgets.
- Active/invisible state follows the public logical open value, not the fade
  animation or temporary QWidget visibility during Closing. Popup modal state
  follows `isModal()` only; `dim` is visual presentation and is not exposed as
  a second modal state.
- An enabled, open Popup-derived surface exposes the custom `dismiss` action
  only when `CloseOnEscape` is allowed. Its key binding is Escape and it uses
  the same close-reason path as keyboard dismissal. CoachMark always exposes
  Escape/dismiss while open.
- Flyout reports that it is controlled by its anchor. TeachingTip and CoachMark
  report that their instructional surface describes the target. Retargeting or
  target destruction changes the relation without rewriting accessible text on
  either object.
- Popup-derived surfaces move focus into the surface and restore the previous
  eligible focus target only when focus has not deliberately moved elsewhere.
  CoachMark remains non-focus-taking; it announces the current help step and
  leaves focus management for actionable child controls to the hosting flow.
- Logical open/close emits one semantic show/hide transition. Help surfaces use
  context-help start/end, CoachMark additionally emits an alert because it does
  not take focus, and changed modal/action/relation state emits only after an
  effective change. Animation frames, placement, paint, and theme changes stay
  silent.
- CoachMark `openChanged` continues to represent logical requested state while
  `opened` and `closed` represent completed fade transitions. Reversing a fade
  does not emit the completion signal for the cancelled direction.

## Menu buttons and auxiliary surfaces

DropDownButton, DrawerView, and ToolTip keep their existing popup and ownership
models while exposing the semantics that their painted chrome cannot provide.

- DropDownButton is one `ButtonMenu`. Without a menu it retains the native
  primary action; with a menu it exposes one `showMenu` action instead of a
  second fake child. Space, Enter, Alt+Down, and F4 use the same popup placement
  path as pointer input. Menu presence and the public `isOpen` value drive
  has-popup and collapsed/expanded state.
- DrawerView is a pane whose active, invisible, collapsed/expanded, and modal
  state follows the observable `isOpen` and `isModal` values. An open drawer
  exposes Escape/dismiss only when `CloseOnEscape` is enabled, keeps caller
  content as real semantic children, and restores an eligible invoker focus
  after dismissal unless focus deliberately moved elsewhere.
- ToolTip uses the tooltip role, falls back to its visible text only while the
  application has not supplied an accessible name, and reports that it
  describes its attached target. Its logical show/hide request changes
  active/invisible state immediately; fade frames remain presentation-only.
- Menu replacement, open/close, modal/policy changes, tooltip text/target and
  logical visibility notify only after effective semantic changes. Repeated
  setters, placement, theme, paint, geometry, and animation frames stay silent.

## Collection paging and splitters

FlipView and SplitView expose the interaction represented by their painted
navigation and divider chrome while retaining caller-supplied page and pane
widgets as real semantic children.

- FlipView is a layered pane with a one-based current-page value, page-count
  bounds, and previous/next actions. Horizontal Left/Right and vertical Up/Down
  use the same navigation path as pointer and wheel input. Its value text adds
  the current page's accessible name when one is available.
- The FlipView adapter filters its paint-only overlay from the accessible tree.
  Authored page widgets remain ordered children, hidden pages retain their
  native invisible state, and descendants of the current page remain
  traversable.
- SplitView is a splitter. Authored pane widgets keep their native roles and
  descendants; each visible boundary adds one private grip child with its
  current pixel position, effective minimum/maximum, and increase/decrease
  actions.
- SplitView grips are real focusable internal widgets so Tab reaches them.
  Arrow keys move by 8 px, Shift+Arrow moves by 1 px, and Home/End move to the
  effective bounds. Keyboard, accessibility actions, and pointer drag share
  the same constrained pane-size path.
- Page changes emit value events, page/pane structure changes emit one reorder
  event, and action events follow effective boundary or orientation changes.
  Paint, hover, animation frames, and repeated setters remain silent.

## Semantic presentation and loading

HyperlinkButton, InfoBar, and Shimmer expose the meaning represented by their
visual treatment without adding application state to the public API.

- HyperlinkButton is a link, not a push button. Its visible text is the anchor,
  its URL is the target and accessible value, and its standard press action
  uses the same click path as pointer and keyboard activation. Successful
  navigation marks the link traversed; changing the URL clears that state.
- InfoBar is one notification whose automatic name combines title and message
  and whose description reports severity. Application-provided accessible
  names and descriptions remain authoritative. Hosted action widgets and the
  real close button remain semantic children while duplicate title/message
  label children are filtered from the notification root.
- Visible InfoBar content or severity updates announce once after an effective
  change. Error is assertive; other severities are polite. Closed or hidden
  bars do not announce updates. The root dismiss action reuses the close-button
  path and its `closed` signal.
- Shimmer is a read-only animation surface with busy state while active. Busy
  does not depend on animation being enabled, so reduced-motion callers retain
  loading semantics. Inactive skeletons are semantically invisible.
- URL/content/severity/open/active and action-availability events follow real
  semantic changes. Shimmer progress frames, painting, layout, theme refresh,
  and repeated setters stay silent.

## Complex custom inputs

ColorPicker, DatePicker, TimePicker, AnnotatedScrollBar, and AutoSuggestBox
retain their existing visual and ownership structure. Their accessibility
adapters describe the custom-painted interaction that already exists; they do
not create persistent widgets for painted values, rows, or markers.

- ColorPicker is one color chooser containing a two-axis saturation/brightness
  spectrum, a bounded hue slider, a selected-color preview, and the existing
  native channel editors and sliders. The spectrum supports Left/Right for
  saturation and Up/Down for brightness; the hue slider supports arrow-key
  stepping. Root and preview values use the same `#RRGGBB` or `#RRGGBBAA`
  representation as the visible Hex editor.
- DatePicker and TimePicker are button-menu roots. Opening state reports
  has-popup plus expanded/collapsed, and the committed value remains distinct
  from the pending flyout value. Each visible flyout column is a bounded spin
  selector with a localized field name, formatted value text, numeric current,
  minimum, maximum, and step. Increase/decrease actions reuse the existing
  Down/Up paths; Enter commits and Escape cancels without changing focus order.
- AnnotatedScrollBar is one bounded vertical scrollbar value plus one logical
  link child for every authored annotation, including labels hidden by visual
  collision filtering. Visible labels expose their painted geometry; filtered
  labels remain in semantic order and report off-screen. Pressing a label uses
  the same scroll-request and `labelActivated` path as pointer activation.
- AutoSuggestBox remains an editable-text interface. It adds autocomplete,
  has-popup, expandable, and expanded/collapsed state, controls its real
  suggestion ListView, and emits active-descendant changes while keyboard focus
  stays in the editor for IME continuity. Alt+Down or F4 opens the list without
  choosing a suggestion; Escape closes it. Query and clear icon buttons have
  translatable accessible names.
- Application-provided root names and descriptions remain authoritative.
  Generated field, channel, action, and marker names are component-owned
  fallbacks only. Value, structure, popup, active-descendant, and action events
  follow effective changes; repeated setters, paint, layout, and theme refresh
  remain silent.

## Baseline and audit order

Repository evidence already covers parts of the contract, including custom
CommandBar/CommandBarFlyout adapters, Field name/description ownership,
InfoBadge and Toast events, FlowView automatic names, navigation descriptions,
date/time action names, and Window caption actions. The audit must classify
each public visible component as:

- **Native:** its Qt base provides the correct role, state, actions, and child
  structure; FluentQt tests only the changed behavior.
- **Augmented:** the native interface is correct, but FluentQt supplies or
  preserves names, descriptions, values, or events.
- **Adapter:** a private `QAccessibleInterface` implementation is required.
- **Gap:** a required semantic, keyboard path, event, or test is missing.
- **Not applicable:** non-visible infrastructure or a pure token/helper.

Audit in this order:

1. Navigation and command surfaces
2. Collections and the DataGrid slices
3. Date/time pickers and editable composite controls
4. Popup, flyout, dialog, TeachingTip, Toast, and other transient surfaces
5. Custom Window chrome and remaining layout/status components

The first pass records evidence and gaps; it does not mechanically add
accessible names or custom adapters to every class. The machine-checked
[Accessibility Inventory](accessibility-inventory.md) is the current result and
must remain complete against the canonical Gallery component catalog.

## Acceptance gates

- A new public visible component has an explicit classification and focused
  role/name/state/keyboard tests before release.
- A changed component cannot overwrite caller-provided accessibility text.
- Custom-drawn interactive children have logical roles, names, state, and
  actions, or use actual child controls with correct interfaces.
- Collection work is proportional to visible logical items and exposes model
  semantics without item widgets.
- Overlay close, focus return, and dynamic announcements match the public state
  machine.
- C++ and PySide6 expose the same application-controlled accessible text and
  ownership behavior for supported public components.
- WASM acceptance records keyboard/focus behavior even where the browser/Qt
  accessibility bridge cannot be treated as equivalent to native desktop.

The 1.7 roadmap tracks the inventory and focused fixes. Full assistive-
technology certification remains a product-level test activity outside the
library's deterministic contract suite.
